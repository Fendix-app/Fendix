# Engine contract reconciliation — 2026-10-03

## Scope and authority

This audit compares executable engine behavior with the current README,
Markdown reference, examples, generated starters and ADR status. The public
stable baseline is tag `v3.4.1`. The inspected development revision is
`d4b2f70` (`v3.5.0-rc.2-4-gd4b2f70`). Executable code and emitted artifacts
win when prose disagrees.

The repository has no `llms.txt` or `llms-full.txt`; there is no engine-local
LLM discovery surface to reconcile. Historical changelog entries and dated
design/audit records remain historical evidence and were not rewritten as
current claims.

## Release boundary

- Stable install and container examples remain pinned to `v3.4.1`.
- The development tree adds managed-CI producer behavior. It is governed by
  ADR-010, whose status authorizes Phase 0 contracts and conformance only. It
  is not a stable product-availability claim.
- The development tree also changes invalid `--fail-on` handling: v3.4.1 logs
  a warning and effectively disables an unknown threshold; development rejects
  it before scanning with exit 2. Both accept `CRITICAL`, `HIGH`, `MEDIUM` and
  `LOW` as executable thresholds, although the v3.4.1 help text omitted `LOW`.

`go/cmd/fendix-app` is a separate long-running HTTP webhook service, not a
Cobra subcommand. It has no flags or positionals. It exposes `POST /webhook`

| `FENDIX_APP_ID` | required positive numeric GitHub App id |
| `FENDIX_APP_PRIVATE_KEY` / `FENDIX_APP_PRIVATE_KEY_FILE` | one required; inline PEM takes precedence over file |
| `FENDIX_WEBHOOK_SECRET` | required |
| `FENDIX_LISTEN_ADDR` | optional, default `:8080` |

| `FENDIX_MAX_CONCURRENT_SCANS` | optional positive integer; unset delegates to handler default `2` |

Configuration or credential failure exits 2, an unexpected serving failure
exits 1, and graceful signal-driven shutdown exits 0. Its scanner behavior is
the child CLI contract above; deployment configuration is documented in
`docs/github-app.md` and the immutable application image manifest lives in
`deploy/fendix-app-release.json`.

Three help contracts were corrected in this reconciliation:

1. `--fail-on` fails when a finding reaches `BLOCK`; independent
   corroboration is not mandatory for a HIGH-band self-evident signal.
2. `--code` auto-enables the Python engine unless
   `--python-engine=false` is explicit. The boolean flag's Cobra default alone
   did not describe the command behavior.
3. `--fast` skips Semgrep and native dependency scanners but does not currently
   suppress the auto-enabled Python phase. This remains a product defect; the
   native-only workaround is `--python-engine=false`.

## SARIF export and import

Export is SARIF `2.1.0`:

- rule `defaultConfiguration.level` and `security-severity` describe intrinsic
  severity;
- result `level` follows the decision (`BLOCK` → `error`, `WARN` → `warning`,
  `INFO` → `note`), with severity fallback for unstamped archived input;
- result `rank` carries effective risk, while result properties preserve
  intrinsic severity, confidence, decision, evidence and provenance;
- the partial fingerprint key is `fendix/v2` for current output; an archived
  report without `fingerprint_algorithm` re-renders under `fendix/v1`;
- `automationDetails.id` is `fendix/scan/<mode>` for recognized modes and the
  legacy `fendix/scan` only when mode is absent/unknown;
- scanner failures/skips and coverage are emitted as invocation notifications
  and run properties.

Import accepts SARIF `2.1.0` only. `ToolID` is the trimmed, lowercased driver
name with spaces changed to hyphens and every character outside
`[a-z0-9._-]` removed; an empty result becomes `unknown-tool`. Runs and files
with the same normalized tool consolidate into one accounting/independence
identity, and mixed versions clear the consolidated version rather than
choosing one. CWE identifiers are extracted only from structured rule
relationships/tags/properties and result taxa, normalized, sorted and deduped.
They populate `Weakness`; the first recognized CWE selects the native category
map, otherwise category falls back to `import/<tool>`.

The importer derives severity from `security-severity` before SARIF level,
skips accepted suppressions, bounds free text and preserves external
fingerprints as provenance only. Imported findings always use
`source: imported`, do not inherit reachability/route/taint claims, and can
corroborate a native finding only through the strong cross-tool path:
independent tool, exact normalized CWE, same normalized location within the
engine's line tolerance.

## Fingerprint and migration contract

`fendix/v2` hashes ordered, labelled semantic identity components with SHA-256
and truncates the result to 20 bytes (40 hexadecimal characters). It excludes
line/column coordinates, title, evidence wording, fix text, severity,
confidence and decision. It retains semantic location: code file, symbol and
operation; secret file and identifier; dependency ecosystem, package and
manifest; or service method and path. Moving a finding between those artifacts
can therefore re-key it. Credential material, including a credential digest,
is never an identity input. Emitters must provide repository-relative paths;
an absolute path is normalized in shape only and remains machine-dependent.

`fingerprint_v1` publishes the retired
`sha1(category|endpoint|title)` identity as a migration bridge only. The engine
does not use it for current matching. Every baseline and every
`.fendix-ignore` `fingerprint:` rule created before v3.0.0 must be regenerated;
endpoint/category suppressions are unaffected. `SEC-NNN` ids are positional,
not durable migration keys. Released changelog entries remain immutable
history.

## Analyzer, check and coverage registries

Coverage registry order is fixed:

```text

python-engine, python-engine/auth, python-engine/injection,
python-engine/deps, plugins
```

Every non-import scan that reaches analyzer/report finalization emits the
eleven base entries exactly once; the three `python-engine/*` children appear
only when the Python protocol reports them. Preflight and usage failures may
exit without a report. In particular, an explicitly requested Python engine
that cannot be resolved exits 2 before registry finalization.

discovered, so no fixed plugin-rule count exists. SARIF imports are normalized
evidence, not a scanner-status registry entry, and import-only mode emits an
empty registry.

The stable ids, category, severity, confidence, CWE, execution/applicability,
evidence and remediation fields for every fixed non-DAST rule, plus the dynamic
native SCA identity model, are enumerated in the
[Check Library executable inventory](check-library-inventory-2026-10-03.md).

Detailed Check Library documentation is still incomplete. `docs/checks/` has
no dedicated page for DAST `configleak`, `cookie-flags`, `idor`,
`open-redirect`, `xss`, `ssrf`, `host-header`, `graphql`, or `method-tamper`,
and no page for native `textscan`. Its secrets page gives examples rather than
all 18 rules, and its AST page is now explicitly labelled as a historical
subset. The executable inventory above closes the contract audit without
inventing new product pages; a later documentation project should generate or
link per-rule pages from these sources.

`scanner_status.state` is `ok`, `skipped` or `failed`. The closed reasons are:

```text
not_applicable, diff_unchanged, disabled_by_flag, disabled_offline,
dependency_missing, unsupported_target, network_error, timeout,
execution_error, malformed_output, truncated_output, input_error, no_endpoints
```

Lifecycle classes are `ok`, `not_applicable`, `disabled`, `unavailable`,
`unsupported`, `failed` and the archived-input fallback `unknown`. Only
`unavailable` and `failed` make `configured_complete=false`. An explicitly
required analyzer is satisfied only by engine class `ok` or `not_applicable`;
disabled and unsupported entries remain required gaps. This standalone-engine
rule is distinct from ADR-010 managed policy, where required managed analyzers
have a stricter completed-and-observed contract.

## Decision semantics

Finding decisions are `BLOCK`, `WARN` and `INFO`. `IGNORE` is reserved in the
internal type; suppression happens before published decisions. Under the
default enforced policy, meeting `--fail-on` is necessary but insufficient:

- LOW confidence band stays WARN;
- no evidence signal stays WARN, even at HIGH;
- MEDIUM needs at least one independent signal;
- HIGH may block with an independent or self-evident signal;
- an unconfirmed-by-live-scan finding needs independent support;
- test-fixture and dependency-applicability rules can further demote according
  to their explicit policy options.

`--enforce-confidence=false` restores severity-only gating and stamps
`policy_override` only when that relaxation changes a verdict. Exit 1 derives
from the same Decision objects serialized into the report. Engine decisions
are finding-level standalone diagnostics; ADR-010's managed release verdict is
backend-authoritative and remains Phase 0/preview work.

## Distribution and integration truth

Official v3.4.1 standalone binaries do not bundle the Python source tree.
`make embed-engine`, including in the release workflow, resets the embedded
directory to `.gitkeep`. Source checkouts may resolve `./python`; official
Docker images copy `/opt/fendix/python/` and set `FENDIX_ENGINE`. Optional
embedded extraction remains compatibility code for legacy/custom builds.

The stable GitHub Action is public and resolvable, but its default execution
path is not currently self-contained: it runs `fendix engine sync` with an
empty `engine_path`, while the downloaded standalone binary has no embedded
payload. A consumer must supply a version-matched engine tree or use the
official container until the Action is fixed.

## Drift guards added

- Generated `.fendix.yaml` is loaded through the real strict parser and must
  carry current decision defaults and all reporter choices.
- The JSON Schema mode and built-in source enums must equal their exact closed
  sets; plugin-source drift remains separately classified as a defect.
- The primary schema Markdown introduction must name
  `reporters.SchemaVersion`, rather than satisfying the check from history.
- README's DAST registry must match every `DefaultChecks()` ID, category, tier
  and order.
- CLI help must state the actual decision, Python auto-enable, `--fast` and
  offline limitation, and flag usage strings cannot create accidental pflag
  metavariables through backticks.
- This audit must contain every explicit root command, every leaf command's
  local flags with their registered types/defaults in its own inventory scope,
  plus Cobra completion.
